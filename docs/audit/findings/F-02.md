# F-02: Admin authentication and session signing are client-side

**Severity:** Medium  
**CVSS v4.0:** not scored — see `../03-methodology.md`.  
**Confidence:** Confirmed  
**Status:** Open  
**Evidence state:** LOCAL_CONFIRMED  
**Build pin:** V4.8.0, SHA-256 `be27a5bc429dec25ec31031cf9128680bcc116b6eaa48c75bdb0e37896234028`

## 1. Overview

This finding was verified against the source-hash-pinned V4.8.0 client build. Evidence comes from captured headers, static source review, or real extracted functions executed in an isolated Node VM with synthetic fixtures. No production state was modified.

## 2. Severity

**Assigned severity:** Medium. **CVSS vector/score:** not scored. Attack prerequisites, complexity, privileges, user interaction, scope and impact are stated qualitatively below rather than converted into an uncalculated numeric score.

- Attack prerequisites: local script execution on the app origin or access to the pinned public bundle; no server credentials.
- Attack complexity: low for the measured paths; the functions execute offline from bundle literals or local state.
- Required privileges: none in the tested client context.
- User interaction: the tester performs the action in their own browser; no victim interaction was tested.
- Scope: browser-local by default; cross-client effects are UNVERIFIED.
- Confidentiality / integrity / availability: see Impact below; no availability impact was measured.

## 3. Status

Confirmed — Open. Evidence state: LOCAL_CONFIRMED.

## 4. Affected components

- `loginAdmin()` (line 31852)
- admin user and password hash literals (2052–2053)
- `computeAdminSessionSig` (4165)
- remembered-session restore (3739–3751)

## 5. Security boundary

Authentication and session issuance must be server-side. A browser cannot prove its own administrator identity.

## 6. Root cause

Login compares bundle-literal hashes and writes a session signature computed from another bundle literal. The restore path checks only that self-computed signature. The credential literal is not republished here.

## 7. Evidence

- `F-02-T01` and `F-02-T04` verify client-side comparison and signature generation.
- `P4-11` and `IV-20` reproduce the session signature offline.
- `f02-session-validation.txt` records the local session validation behavior.

All evidence files are sanitized and indexed in `../evidence/README.md`. No real credential, real user record or production packet body is stored.

## 8. Reproduction prerequisites

- Pinned V4.8.0 source.
- Own browser origin and synthetic admin fixture.
- No real credential is used or stored in this report.

## 9. Reproduction steps

1. Inspect the client hash comparison path.
2. Reproduce the admin session signature from bundle data.
3. Set the session in local storage and invoke remembered-session restore.
4. Confirm admin-gated UI functions become reachable, then restore state.

## 11. Expected behavior

Admin login must require a server-authenticated credential and a server-issued session that the client cannot mint.

## 12. Actual behavior

A locally computed signature restores admin state and passes the client's own checks.

## 13. Impact

Any user able to run script on the origin can enter the local admin UI and reach downstream local admin actions (see NEW-15). No server audit trail is produced.

## 14. Attack scenario

A student uses the bundle's hash helper and salt literal to mint a session, reloads, and sees the administrator interface.

## 15. Remediation

1. Move authentication to a server with Argon2id or bcrypt hashes and constant-time verification.
2. Issue short-lived server sessions in `HttpOnly; Secure; SameSite=Strict` cookies.
3. Add server-side rate limiting and audit logging.
4. Rotate all admin hash and salt literals.
