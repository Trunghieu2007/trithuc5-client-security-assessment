# F-05: Device lock and Gmail binding are enforced from client-owned fields

**Severity:** Medium  
**CVSS v4.0:** not scored — see `../03-methodology.md`.  
**Confidence:** Confirmed  
**Status:** Partially Fixed  
**Evidence state:** LOCAL_CONFIRMED (partial fix)  
**Build pin:** V4.8.6, SHA-256 `ffe94aea9b327853b0b8836bf0d52e1f509fcc68c007bead7b8a888604389185`

## 1. Overview

This finding was verified against the source-hash-pinned V4.8.6 client build. Evidence comes from captured headers, static source review, or real extracted functions executed in an isolated Node VM with synthetic fixtures. No production state was modified.

## 2. Severity

**Assigned severity:** Medium. **CVSS vector/score:** not scored. Attack prerequisites, complexity, privileges, user interaction, scope and impact are stated qualitatively below rather than converted into an uncalculated numeric score.

- Attack prerequisites: local script execution on the app origin or access to the pinned public bundle; no server credentials.
- Attack complexity: low for the measured paths; the functions execute offline from bundle literals or local state.
- Required privileges: none in the tested client context.
- User interaction: the tester performs the action in their own browser; no victim interaction was tested.
- Scope: browser-local by default; cross-client effects are UNVERIFIED.
- Confidentiality / integrity / availability: see Impact below; no availability impact was measured.

## 3. Status

Confirmed — Partially Fixed. Evidence state: LOCAL_CONFIRMED (partial fix).

## 4. Affected components

- `verifyAndBindStudentDeviceOnLogin`
- `setSimulatedDeviceSlot` (line 31257)
- user fields `trustedDevices`, `maxDevices`, `gmail`, `status`

## 5. Security boundary

Device registration must be atomic and server-held. The browser must not decide whether its own device is trusted.

## 6. Root cause

The limit check reads client-writable user fields. V4.8.6 gates the test-only setter behind `requireAdminAuth`, but that gate is itself client-side and the underlying fields remain writable.

## 7. Evidence

- `F-05-T01`…`F-05-T05` exercise the local limit and binding logic.
- `poc-suite-validation.txt` verifies the DISPLAY default does not mutate state.

All evidence files are sanitized and indexed in `../evidence/README.md`. No real credential, real user record or production packet body is stored.

## 8. Reproduction prerequisites

- Synthetic student fixture.
- Local VM or browser console.

## 9. Reproduction steps

1. Display the local device fields and observed limit decision.
2. Optionally run the opt-in local action to change `maxDevices`.
3. Re-run the binding check and observe the altered decision.
4. Restore state.

## 11. Expected behavior

Device slots and bindings must be registered by a server with out-of-band verification for new devices.

## 12. Actual behavior

The display PoC shows the decision derives entirely from local fields; the opt-in action changes the decision locally.

## 13. Impact

A user can misrepresent trusted device state in their own client. Server-side concurrency and quota enforcement are not present in the measured surface.

## 14. Attack scenario

A user edits their local `maxDevices` value before login and avoids the client-side block on adding another device.

## 15. Remediation

1. Store device registrations server-side and enforce them atomically.
2. Require out-of-band verification for new devices.
3. Remove local-only test setters from production or gate them server-side.
