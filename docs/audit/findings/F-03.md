# F-03: VIP entitlement is decided entirely in client-side JavaScript

**Severity:** High  
**CVSS v4.0:** not scored — see `../03-methodology.md`.  
**Confidence:** Confirmed  
**Status:** Open  
**Evidence state:** LOCAL_CONFIRMED  
**Build pin:** V5.4.6, SHA-256 `2dbf781e4febf2e47a78da81352227de30c4972a8f0491e4864bdb32e370f61c`

## 1. Overview

This finding was verified against the source-hash-pinned V5.4.6 client build. Evidence comes from captured headers, static source review, or real extracted functions executed in an isolated Node VM with synthetic fixtures. No production state was modified.

## 2. Severity

**Assigned severity:** High. **CVSS vector/score:** not scored. Attack prerequisites, complexity, privileges, user interaction, scope and impact are stated qualitatively below rather than converted into an uncalculated numeric score.

- Attack prerequisites: local script execution on the app origin or access to the pinned public bundle; no server credentials.
- Attack complexity: low for the measured paths; the functions execute offline from bundle literals or local state.
- Required privileges: none in the tested client context.
- User interaction: the tester performs the action in their own browser; no victim interaction was tested.
- Scope: browser-local by default; cross-client effects are UNVERIFIED.
- Confidentiality / integrity / availability: see Impact below; no availability impact was measured.

## 5. Security boundary

Entitlement checks must consult an authoritative server. The in-client 'vault' is a consistency structure, not a trust anchor.

## 6. Root cause

The vault is an in-memory map rebuilt from client-owned records. All gate inputs, including signature and seal fields, are writable from the same privilege level as the gate itself.

## 7. Evidence

- `IV-05`, `IV-06` and `IV-09` show self-sealed synthetic records passing all three gates.
- `P4-16` completes the full chain with zero server calls.
- `poc_f03_vip_entitlement.js` is executed by `poc-suite-validation.txt` with documented restore behavior.

All evidence files are sanitized and indexed in `../evidence/README.md`. No real credential, real user record or production packet body is stored.

## 8. Reproduction prerequisites

- Own browser and synthetic student fixture.
- No real account or payment transaction.

## 9. Reproduction steps

1. Start with a non-VIP synthetic record and confirm all gates deny.
2. Forge `_sig` and `_adminVipSeal` using the bundle's own helpers.
3. Re-run boot normalization and register the record in the client vault.
4. Call the three gates and observe them return true.
5. Restore local state.

## 11. Expected behavior

A local write to user fields must never change entitlement. The server should be the only source of VIP status.

## 12. Actual behavior

Local artifact forgery changes entitlement for every measured gate, including protected-action verification and the backend grant token.

## 13. Impact

VIP-only lessons, packages and actions are unlockable without authorization. Because the decision is client-side, no server log or rate limit can observe it.

## 14. Attack scenario

A user modifies their own client record before boot and receives VIP UI and functionality. The app behaves as though a teacher approved the request.

## 15. Remediation

1. Fetch entitlement from an authenticated server on every sensitive action.
2. Remove client-minted backend tokens and treat any client-held token as untrusted until verified server-side.
3. Keep only a cache of server decisions, invalidated on logout and short expiration.
