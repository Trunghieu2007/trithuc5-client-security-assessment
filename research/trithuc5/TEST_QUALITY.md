## 1. Function extraction

**Weakness found.** `extractFunction` counts `{` and `}` character by character. It does not
understand braces inside strings, template literals, or comments. A future source change could
therefore stop at the wrong brace and still produce syntactically valid code.

**Mitigation added.** `H-01` verifies that nine security-critical extracted functions:
- begin with the expected `function <name>(` signature, and
- parse as standalone JavaScript via `vm.Script`.

This does not fully solve the lexer problem. It is documented as a known harness limitation;
the source hash gate prevents silent reuse against a different build.

## 2. Dependency completeness

Extracted functions run with real source code for storage helpers, hashing, serialization,
packet processing, device binding, and integrity checks. UI/logging functions
(`showToast`, `renderApp`, `logStudentActivity`, `saveDraftAnswers`,
`finalizeExamSubmission`) are stubbed and their calls are recorded. This is sufficient for
state-transition assertions but not for visual/DOM behavior. `F-06` is therefore static only.

## 3. Mock storage semantics

The harness provides localStorage, sessionStorage, a cookie jar, `window.name`, and the
in-memory fallback used by `safeStorageGet`. `safeStorageRemove` now behaves like a browser for
cookie deletion (`max-age=0`). Quota errors, storage-event ordering, and cross-origin isolation
are not modeled. `A-04-T02` manually dispatches a storage event into a second VM; it proves
state replacement and persistence in the harness, not real browser scheduling.

## 4. Mock fetch

Mock fetch returns plausible ntfy `/json?poll=1`, KV `GetValue`, and KV `UpdateValue` responses
and records calls. It does not model ntfy retention, SSE chunking, HTTP failures, or broker
authorization. No test may be read as proof of live ntfy/KV delivery. This is why `F-01-T11`
was renamed to "two isolated VM environments accept the same packet (NOT proof of live ntfy
delivery)".

## 5. Security outcome vs source-string assertions

- **Behavioral tests** execute extracted source functions and assert state transitions:
  F-01-T01…T13, T15…T17, F-02-T01…T04, F-03-T01…T03, F-04-T02, F-05-T01…T05, A-04-T02.
- **Static tests** assert source structure only and are named or labeled `(static)`:
  F-01-T14, F-02-T05, F-04-T01/T03, F-06-T01, A-01-T01, A-02-T01, A-03-T01, A-04-T01, H-01.

Severity conclusions must not rest on static tests alone where a behavioral test exists.

## 6. Self-proving tests

**Corrected:** `F-01-T11` previously claimed "public topic has no cross-browser isolation".
The test builds two VMs and passes a packet manually. That proves both VMs accept the same
packet; it does not establish live topic delivery or production cross-client impact. The title
and assertion message were corrected, and the evidence level in the matrix is limited to
local behavioral reproduction.

## 7. Valid and invalid input coverage

Covered: valid signature, missing signature, invalid signature, missing `fromAdmin`, forged
`fromAdmin`, duplicate, expired timestamp, stale privileged packet, malformed tombstone,
unauthorized deletion, user injection by multiple types, malformed user entries, and
cross-tab state replacement.

Not covered: protocol-level ntfy malformed frames, KV chunk truncation, and real browser race
timing. These remain `UNVERIFIED`.

## 8. Can the harness detect a remediation?

The vulnerability tests would fail after a patch, but failing tests alone are weak evidence of
secure behavior. `tests/secure_controls.js` adds nine acceptance controls asserting secure
outcomes: valid signed packet succeeds; unsigned/invalid/expired/replayed/unauthorized packets
fail; no password in public packets; cross-account packets do not mutate unrelated accounts.
Two controls are partly structural (`SC-05` replay cache, `SC-09` target-account field) because
the current client exposes no server verifier API. This is documented rather than hidden.

## 9. Evidence log consistency

- `evidence/README.md` incorrectly said 34 tests; corrected to 40 behavioral/static checks plus
  9 secure controls.
- `evidence/test-results.txt` now matches the current `run_all.js` output exactly.
- `poc/last_run.log` and `evidence/test-results.txt` are different suites. Both read the same
  hash-pinned source, but the PoC is an earlier targeted demonstration and the suite is the
  authoritative regression set. They are not expected to have identical line counts.

## Known limitations

- No real browser automation was run; DOM/anti-cheat conclusions are static.
- No production packets were read or sent; all cross-client claims are local simulations.
- Mock fetch cannot validate server-side authorization because no server API exists in the
  measured client.
